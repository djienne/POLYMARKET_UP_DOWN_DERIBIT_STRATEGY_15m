The audit found substantive problems in the contract model, live order handling, recovery watchdog, grid decision cadence, paper execution assumptions, and dashboard updates. Passing tests do not cover several of these failure paths. The first priorities are the TWAP payoff mismatch, ambiguous order submissions, watchdog stop semantics, and grid latency.

Scope: current working-tree source and configuration; local Docker runtime; model and trading pathways; persistence and accounting; dashboard backend/frontend; deployment scripts; dependency consistency; tests and operational documentation. Runtime observations below were collected around 07:44–07:55 UTC. Existing local changes were preserved. This audit added this report; it did not edit application code/configuration, restart production services, or submit orders.

**Confirmed findings, ordered by urgency.** P1 means a high-impact issue requiring prompt correction. P2 means a substantive correctness or reliability issue.

1. **[P1] The production model prices terminal spot, but the active contract specifies a 60-second TWAP.** [terminal_probability.py:439](BTC_pricer_15m/btc_pricer/models/terminal_probability.py#L439) evaluates an indicator on final simulated spot prices. [chainlink_feed.py:303](BTC_pricer_15m/scripts/trader/chainlink_feed.py#L303) accepts the instantaneous Chainlink topic, excluding the separate TWAP topic. At 07:52:38 UTC, the one-second-old calc snapshot selected `btc-updown-15m-1788594300`, the active 07:45–08:00 UTC market. Its [Gamma record](https://gamma-api.polymarket.com/markets/slug/btc-updown-15m-1788594300), fetched through a read-only Docker request, specified `btc-usd-twap-60s-streams` as its resolution source and described a TWAP outcome. [Polymarket documents a separate 60-second TWAP feed](https://docs.polymarket.com/market-data/chainlink-twap). Thus `P(S_T >= K)` is not the specified payoff probability. [Settlement logic](BTC_pricer_15m/scripts/trader/calc_daemon.py#L1048) also substitutes the next window's opening price, with instantaneous feed fallbacks. Model the declared payoff and consume the authoritative oracle output. Its exact custom sampling/weighting is not published, so a homemade rolling average should not be treated as equivalent. **Evidence limit:** all 13 recent finalized winners sampled agreed with Gamma; this audit did not demonstrate a historical wrong settlement or quantify the trading loss from the model mismatch.

2. **[P1] A timed-out order response can lead to repeated buys without a tracked pending entry.** The broad exception handler in [executor_live.py:1262](BTC_pricer_15m/scripts/trader/executor_live.py#L1262) returns failure with no order ID and `ambiguous=False`, even after submission has begun. [single_trader.py:4380](BTC_pricer_15m/scripts/trader/single_trader.py#L4380) consequently permits retries; pending-entry persistence at line 4528 requires both an ID and ambiguity. A network-isolated Docker reproduction ran the real executor and entry retry paths against a mock venue that accepted each submission before raising `ReadTimeout`: six accepted submissions, zero tracked positions, no pending entry, and `ambiguous=False`. Retry delays were shortened to zero for this reproduction; production allows five retries with a 30-second window. Preserve the submitted order identity/intent and reconcile uncertain acceptance before allowing another buy. Merely setting the ambiguity flag is insufficient while pending tracking requires a returned ID.

3. **[P1] The safety watchdog's stop interlock clears itself after one poll.** [stack_liveness.py:353](BTC_pricer_15m/scripts/stack_liveness.py#L353) updates `last_recovery` even when recovery did nothing because live was held. On the next poll the safety trigger is older than that timestamp, allowing live to restart. An isolated Docker reproduction with mocked Docker actions held live at t=101, then started it at t=161. Deployed source matches the working tree. Keep a safety stop latched until deliberately cleared; an empty or unrelated recovery cannot acknowledge it.

4. **[P1] An intentional live stop is also reversed by the passive watchdog.** [live_manager.py:178](POLYMARKET_STREAMING_DASHBOARD_15m/live_manager.py#L178) stops live and records `.live_location=stopped`. [stack_liveness.py:43](BTC_pricer_15m/scripts/stack_liveness.py#L43) always expects the live container and does not consult that desired state or the Compose profile. With the watchdog active, a live-only stop can be reversed on the next approximately 60-second poll. Starting a paper stack can likewise revive an existing stopped live container. Desired operating mode and explicit stops must govern recovery separately from fault recovery.

5. **[P1] Reporting work blocks the grid for minutes between decisions.** [main.py:940](BTC_pricer_15m/scripts/trader/main.py#L940) runs leaderboard generation synchronously even when snapshot writing is asynchronous. [summary.py:164](BTC_pricer_15m/scripts/trader/summary.py#L164) reparses the entire 381,107,348-byte trade history on each save. A disposable Docker benchmark of this exact function against actual read-only data took 14.541 seconds wall time and 8.803 seconds CPU at one CPU. Under the deployed [0.1-CPU quota](BTC_pricer_15m/docker-compose.yml:162), that CPU demand alone requires approximately 88 seconds of quota time. Observed grid ticks #419–#433 spanned 06:56:25–07:49:46 UTC: about 3.8 minutes per increment. At 07:49:46 the grid was still handling the market ending 07:45, although calc/live had switched by 07:45:43. Approximately 99.63% of grid CPU accounting periods had experienced throttling. Maintain last-close metadata incrementally and move reporting out of the decision path, then verify actual cadence under a suitable CPU budget. Fresh background feeds do not establish fresh trading decisions.

6. **[P1] A staged paper entry can execute after its supporting probability disappears.** [trader.py:969](BTC_pricer_15m/scripts/trader/trader.py#L969) starts finalization with the old probability, replacing it only for `local_mc_cdf` values strictly between zero and one. Docker reproductions used current config and mirror instance 1271, staging at probability 0.85. Final probability `0.00/local_mc_cdf`, `0.01/event_scalar`, and `0.50/no event` all produced an entry retaining 0.85; `0.01/local_mc_cdf` correctly rejected. Final ticks had no entry signals. This can create paper trades and live mirror instructions from a vanished edge. Accept valid endpoint probabilities and require usable current model evidence at finalization.

7. **[P2] Growing trade-history corrections can stall the dashboard indefinitely.** [trades_tail.py:691](POLYMARKET_STREAMING_DASHBOARD_15m/backend/app/collector/trades_tail.py#L691) recognizes same-size rewrites but treats larger files as append-only. The live trader performs variable-length atomic corrections. In Docker, changing `TP_FILLED` to `VOIDED_PHANTOM_TP` grew a fixture from 225 to 233 bytes; three successive polls raised validation errors from the old byte offset, and the cached phantom +$5 close survived. Existing tests preserve byte count artificially. Detect replacements/changed consumed content before assuming growth means append, and recover rather than retrying the same malformed offset forever.

8. **[P2] Paper TP fills ignore available quantity in the production liquidity mode.** [trader.py:1127](BTC_pricer_15m/scripts/trader/trader.py#L1127) checks sellable quantity only when consuming liquidity across instances. Production uses `liquidity_mode=independent`. A Docker reproduction fully closed 100 shares at TP and booked $13.85 although both current and delayed books had only 0.01 bid shares. Independent experiments should each have an independent liquidity budget; each position still needs a quantity-aware fill model. A quoted touch alone does not establish a complete maker fill, so paper TP rates and resulting mirror instructions are optimistic under this assumption.

9. **[P2] Flat paper friction does not represent current fees.** [trader.py:762](BTC_pricer_15m/scripts/trader/trader.py#L762) adds 1% to entry cost; line 1231 deducts 1% from non-expiry exits, including modeled maker TPs. The same active market's Gamma record returned `feeSchedule={exponent:1,rate:0.07,takerOnly:true,rebateRate:0.2}`. [Official fees](https://docs.polymarket.com/trading/fees) imply $1.75 for a 100-share taker trade at $0.50, versus the grid's $0.50; maker fees are zero. This biases comparisons differently by price and exit type. Represent market-specific fees and maker/taker execution separately from additional slippage/friction assumptions. Do not retroactively apply today's fee schedule to all historical trades.

10. **[P2] Shared feed activity can hide a dead live trader.** [liveness.py:117](POLYMARKET_STREAMING_DASHBOARD_15m/backend/app/collector/liveness.py#L117) considers grid state and shared calc files as live heartbeat candidates. A Docker fixture with one-hour-old live state and lock, but fresh shared calc output, returned `bot_live=true` and age zero. Use live-owned heartbeat freshness and separate process/container evidence. Preserve configured live mode when stale; show its status accurately.

11. **[P2] Dashboard helper reads can suppress state and entry events.** [state_hub.py:350](POLYMARKET_STREAMING_DASHBOARD_15m/backend/app/api/state_hub.py#L350) and bootstrap at line 519 consume `read_if_changed()` on the reader used by the publishing loop. A normal live-open transition emitted `state.update` and `trade.append`; the identical transition emitted neither when the slug helper read first. Another client's bootstrap can trigger the same race. Centralize change consumption/publication and make ordinary cached reads non-consuming.

12. **[P2] Recovery proceeds after dependency health waits fail.** [stack_liveness.py:257](BTC_pricer_15m/scripts/stack_liveness.py#L257) logs unhealthy dependencies but continues to subsequent tiers. An isolated Docker fixture in which every health wait failed still started Redis, calc, and live and returned success. Existing unhealthy containers are also skipped when checking only stopped targets. Treat required dependency failures as incomplete recovery and gate dependent starts accordingly.

13. **[P2] Watchdog backoff can become permanent after transient failures.** After three failed recoveries, [stack_liveness.py:333](BTC_pricer_15m/scripts/stack_liveness.py#L333) skips all further recovery while any expected service remains down. A changed failure set does not reset the count despite the log saying it waits for changes. Use a bounded retry interval or reset on meaningful dependency/state recovery while preserving explicit live-stop intent.

14. **[P2] The all-stack management commands omit the spot service.** [manage.py:25](manage.py#L25) and `STOP_ORDER` omit `spot`. Thus an all-stack stop leaves it running after Redis stops, and explicit restart/recreate coverage misses it. The dashboard subdirectory's service lists have the same omission. Include the actual full service set in lifecycle operations and test the resulting commands.

**Other concerns and evidence limits.**

- The undefined-name smoke test skips because `pyflakes` is absent from the Docker environment. Frontend behavioral tests are not configured. Passing the existing suites therefore leaves relevant coverage gaps.
- Frontend `npm audit` reported seven development-tool vulnerabilities, including four high; excluding development dependencies reported zero. The deployed frontend is static output, so this does not establish an exploitable production endpoint. The emitted JS bundle is approximately 756 KB minified / 221 KB gzip and generates a size warning.
- Dashboard Docker socket access remains privileged despite a `:ro` mount: the mount does not restrict Docker API methods. Localhost-only dashboard binding is present. No exploitable dashboard route was established; a socket proxy with only necessary read operations would narrow this boundary.
- [OPERATIONS.md:17](OPERATIONS.md:17) incorrectly describes intentional live-to-dry-run fallback; related stale instructions appear later in the file. The README's 864-instance description also omits the configured stop-loss extension; current runtime has 1,296 instances.
- Reactive watchdog protection was not established from the default PID/trigger files; absence of those files is insufficient to rule out an independently configured process.
- Out-of-sample probability calibration, sensitivity to the short-horizon volatility extrapolation, local-CDF approximation error, and strategy selection bias remain unquantified here. Matching another simulation would not establish correctness. After correcting payoff and execution semantics, validate against oracle outcomes, proper probability scores, fee-adjusted fills, and separate evaluation data.
- VPS/offload configuration was reviewed statically; remote runtime behavior was not exercised. This audit did not perform a full historical security scan, exhaustive provider fault injection, or long-duration soak. The report distinguishes reproduced defects from these remaining uncertainties.

The implementation order should first restore the correct contract/payoff and safe live submission/stop behavior, then restore timely grid decisions and realistic fills/fees, and finally repair dashboard event delivery and remaining recovery/documentation gaps. Re-run the relevant Docker suites after fixes, rebuild/recreate as required by project instructions, and verify actual live/grid decision freshness and accounting on representative data.
